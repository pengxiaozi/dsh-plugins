# SKILL: plan-gate（先方案、后动手）

> AI LOAD INSTRUCTION: 这是一个"执行前闸门"。用户的第一个需求消息到来时，**先别改代码**；用一两分钟做只读侦察，然后按下面的固定结构给出方案 + 文件清单，用 ask_user_question 请用户确认。确认后再执行。**同一个需求只做一次**，后续追问不要再重复整套方案。

## 1. 何时触发 / 何时不触发

**触发（满足全部）：**
- 用户第一次描述一个开发类需求（改代码、加功能、修 bug、改页面/样式/接口/配置、重构等）；
- 当前上下文里还没有针对这个需求给出过方案并得到确认。

**不触发：**
- 同一需求确认后的后续追问、补充细节、报错跟踪；
- 纯咨询、解释、代码阅读、方案讨论（用户没让你改）；
- 用户明确说"直接改 / 不用确认 / 按你说的做"——直接执行，但仍要先用一句话复述范围，并列出要改的文件；
- 单字符/单行级别的明确小修（如"把标题改成 X"），一句话复述 + 直接改即可。

**"只第一次"的红线：**
- 同一个需求只出一次完整方案；确认后进入执行，**不要每一步都问"要不要继续"**；
- 只有出现以下情况才再确认一次：用户提出**新的独立需求**；或执行中发现必须**超出已列文件范围**（此时只追加"增量方案 + 新增文件"，不要重发整套）。

## 2. 允许的只读侦察（不改文件）

出方案前可以做**只读**动作把文件清单弄准：
- read / grep / glob 目标代码；
- 只读 shell（Get-ChildItem、Select-String、git status/diff 等）；
- **禁止**在确认前 write/edit/mkdir/mv/rm，禁止跑构建/部署/长任务。

侦察控制在必要范围；如果确实看不完，就在方案里标记"待确认项"，不要瞎猜路径。

## 3. 首次回复的固定结构（一次给全）

按以下 5 块输出，中文，正文控制在 250 字左右（表格不计）：

1. **理解**：一句话复述需求（"我理解你要的是……"），方便用户纠偏。
2. **做法**：3–7 步、按执行顺序、每步一句，写清先后依赖。
3. **涉及文件**：表格，**必须具体到文件路径**；标注操作与作用：

   | 操作 | 文件 | 改什么 |
   |---|---|---|
   | 修改 | `src/pages/school/expert/index.vue` | 查询区加高校下拉、列表联动 |
   | 修改 | `application/controllers/school/Info.php` | lists 方法接收 school_id 并过滤 |
   | 新建 | `application/views/...` | （如确实需要） |

   路径不确定的标 `?` 并说明原因；按"前端 / 后端 / 配置 / 测试"分组或加"端"列。
4. **假设与风险**：最多 3 条，尤其写出"会改变范围"的假设（如"假设 school_id 字段已存在"）。
5. **不做的事**：明确边界（"不改导入导出/不动详情页"），防止范围膨胀。

最后**必须**用 `ask_user_question` 请求确认：

```json
{
  "questions": [{
    "id": "confirm-plan",
    "header": "确认方案",
    "question": "按上面的做法和文件清单执行吗？",
    "options": [
      { "label": "执行（推荐）", "description": "按方案和文件清单开始改" },
      { "label": "先调整", "description": "我会告诉你改哪一步/哪些文件" },
      { "label": "取消", "description": "先不改" }
    ]
  }]
}
```

用户选"先调整"时：只针对差异重新给**增量方案**（改哪步、加/减哪些文件），然后再确认，不要整篇重发。

## 4. 确认后的执行规则

- 先 `todo_write`：第一项"方案已确认"，其余为方案步骤（可勾选）；
- 只改清单内的文件；发现清单外的问题 → 记入"后续项"，**不顺手改**；
- 需要超出清单（新增文件/改公共组件/动数据库/动配置）→ 暂停，给**增量方案 + 新增文件**，确认后再继续；
- 用户说"不用确认了"后，不再出方案，直接按当前理解执行，但仍按上面的文件边界执行；
- 交付时给**对账表**：每条用户要求/验收点 → 改在哪个文件（+ 关键位置）+ 静态自检结果；
- 遵守项目自身规则（例如：不主动跑构建、不用浏览器工具、不造测试数据），需要验证时由用户执行。

## 5. 输出示例（缩略）

> 理解：专家列表查询区加"所属高校"筛选，按 school_id 过滤。
>
> 做法：① 确认 school_id 字段与字典来源 → ② 前端查询区加下拉 → ③ 列表请求携带参数 → ④ 控制器接参并过滤 → ⑤ 静态自检。
>
> 涉及文件：
> | 操作 | 文件 | 改什么 |
> |---|---|---|
> | 修改 | src/pages/school/expert/index.vue | 查询区下拉 + 请求参数 |
> | 修改 | application/controllers/school/Info.php | lists 接收并过滤 school_id |
>
> 假设：school_id 已在 expert_info 表；字典在 myconfig.php 的 school_list。不做：不改导入导出、不改详情页。
>
> （随后 ask_user_question 请确认）

## 6. 反例（不要这样）

- 先改代码再补方案；确认前就 write/edit；
- 方案写成 20 行作文，或只说"我会优化相关文件"而不给具体路径；
- 确认后每一步都问"要继续吗"；
- 每个新消息都重新出一遍完整方案（只在新需求或范围变化时增量确认）；
- 文件表里写"多个文件""相关页面"这种模糊项。
